Operating Principles

The core runtime model.

I

Isolation is the default

Each agent gets its own filesystem, a MUS pipe to `keeperd`, and a firewalled path to its configured LLM API endpoint only.

II

`keeperd` is the authority

`keeperd` owns policy, routing, approvals, credential resolution, and audit. It decides whether a well-formed request is allowed.

III

Capabilities are explicit

Agents do not receive broad default access. They receive named capabilities with scopes, denials, and operator-visible contracts.

IV

Audit is built in

MUS-framed traffic and structured events are recorded for inspection. `vivlog` exists so operators can see what the runtime actually did.

Architecture

One control plane, one agent, one audit path.

Keeper

The policy and routing authority. It stamps identity, enforces policy, resolves credentials, writes audit records, and mediates external access.

Ward

The syntax and protocol adapter at the agent boundary. It turns backend-specific tool syntax into MUS requests, rejects malformed calls, and reports local execution facts.

Operator

The operator has live state, prompt dispatch, event traces, and a CLI-first path into the logs.

Included in the MVP

What the MVP actually includes.

  • 01 Single-agent runtime core
  • 02 `keeperd` as policy and routing authority
  • 03 `ward` as syntax and protocol adapter
  • 04 Browser and filesystem capabilities with audit and debug tooling

Excluded for now

What it does not try to do yet.

  • -- No raw credentials inside the agent
  • -- No unrestricted network egress
  • -- No GUI dependency in the container runtime
  • -- No multi-agent orchestration in the MVP
